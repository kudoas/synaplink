# 読み込めないメモの確認と再試行

この文書は、一覧の部分読込失敗をどう確認し、再試行するかを説明する。元の再現条件は[調査M08](../investigations/2026-11-14/README.md)を参照する。

## 一部のメモを読めない場合

一覧取得は、読めたメモと、読めなかった項目のパス・理由を同じ応答で返す。読めたメモは引き続き開いて編集できる。読めない項目は一覧・検索に含まれず、一覧下部に件数と警告を表示する。「対象と理由を表示」で詳細を確認できる。

一覧取得では文字コードの変換、ファイルの削除、権限の変更を行わない。元ファイルのコピーを確保し、表示された理由を確認してから外部のツールで修復する。「一覧を再読込」または既存の2.5秒周期の更新で再試行し、読込が成功すると警告は消える。

対象は既存どおり、保存先直下の`.txt`通常ファイル（有効なシンボリックリンクを含む）。非`.txt`項目、ディレクトリ、特殊ファイルは警告に数えない。`.txt`の状態取得失敗、個別読込失敗、フォルダ列挙中のエラーを報告する。フォルダ自体を開けない場合は部分成功にせず従来の全体エラーを返し、更新時の表示中一覧を保持する。

## 一覧と警告の整合性

内部IPCの`list_notes`は配列から`{ notes, issues }`へ変更した。フロントエンドの`api.listNotes`は配列を返す従来形を維持し、警告が必要な呼出元は任意のコールバックを渡す。Appは応答をローカルに保持し、保存先と要求世代が有効な場合だけ一覧と警告を一緒に反映する。旧保存先や古いポーリング応答の警告は反映しない。バックエンドとフロントエンドは同じアプリのビルドとして更新する。

## 確認した範囲

`3547156`の実ファイル再現では、UTF-8の`valid.txt`と`0xff`の`invalid.txt`の2件から、警告なしの成功として1件だけ返った。追加した回帰試験は修正前に失敗し、修正後は読めた1件と失敗1件を返し、両ファイルのバイト列が不変であることを確認した。

Rust試験では列挙途中のエラーを注入し、有効なリンク・壊れたリンク・非対象項目・全件失敗・保存先不在も確認した。権限拒否の実OS再現は未実施。AppのAPIモック試験では有効メモを開けること、手動再試行で警告が消えること、再試行の全体失敗では警告と表示中メモ・編集可能状態を保持してエラーを知らせること、同じ保存先と別保存先の応答逆転で古い警告が復活しないことを確認した。ネイティブ画面での表示確認は未実施。
